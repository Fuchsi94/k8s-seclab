# gcp-sec-lab

A 2-node kubeadm cluster (1 control plane + 1 worker) on GCE VMs (Ubuntu 24.04, Kubernetes 1.36, Cilium 1.20), used as
the base for the security AI agent lab (see [docs/roadmap.md](docs/roadmap.md)).

`terraform apply` brings up a working cluster: the startup script installs
containerd + kubeadm, the control plane runs `kubeadm init` and installs
Cilium, and the worker joins automatically.

## First time

1. Put your public **IPv4** into `terraform.tfvars`:
   ```bash
   echo "$(curl -4 -s ifconfig.me)/32"
   # your_ip = "X.X.X.X/32"  -> SSH (22) and API (6443) only from you
   ```

2. Apply:
   ```bash
   terraform init
   terraform apply
   ```

3. Wait ~5 min. The bootstrap is done when this file exists on both nodes:
   ```bash
   ssh $(terraform output -raw control_plane_ip) "ls /var/lib/gcp-sec-lab-ready"
   ```
   Logs: `sudo journalctl -u google-startup-scripts -f`

4. Get the kubeconfig on your laptop:
   ```bash
   eval "$(terraform output -raw fetch_kubeconfig)"
   export KUBECONFIG=~/.kube/gcp-sec-lab
   kubectl get nodes   # both Ready once Cilium is up
   ```

## How the bootstrap works

`scripts/install-common.sh` is rendered once per role and runs as root on
**every boot**. Each step checks first whether it already happened:

| Step | Runs on | Skipped when |
|---|---|---|
| Install containerd, conntrack, kubeadm/kubelet/kubectl | both | `kubeadm` is installed |
| `kubeadm init` (public IP as cert SAN) | control plane | `/etc/kubernetes/admin.conf` exists |
| Create join token (Terraform-generated) | control plane | token exists |
| Install cilium CLI + Cilium (Hubble relay on) | control plane | `cilium` DaemonSet exists |
| Copy kubeconfig to `ssh_user` | control plane | `~/.kube/config` exists |
| Wait for API server, `kubeadm join` | worker | `/etc/kubernetes/kubelet.conf` exists |

The join token is generated by Terraform (`random_password`) and passed to
both scripts. The worker joins **without CA pinning**
(`--discovery-token-unsafe-skip-ca-verification`), which is acceptable inside
the lab network. Caveats:

- The token lives in the Terraform state and in the VM metadata. Anything
  that can reach the metadata server (including pods!) can read it while it
  is valid (24h; the control plane re-creates it on every boot). Blocking
  `169.254.169.254` for pods is a later hardening step.
- To add a node after 24h, reboot the control plane or rerun its startup
  script; that re-creates the token.

Re-run the script by hand (e.g. after `kubeadm reset`):
```bash
sudo google_metadata_script_runner startup
```

## Notes

- The control plane public IP is **ephemeral**: it changes when the VM is
  stopped/started or recreated. The cert SAN and kubeconfig then no longer
  match; `kubeadm reset` + rerun the script, or re-issue the apiserver cert.
- Changing `k8s_version` or the script only updates the VM metadata in place.
  Running VMs keep their installed version; it applies to new VMs.
- If your IP changes, update `your_ip` and `terraform apply`. Only the firewall
  rules change.
- The VMs are in the `default` VPC, which has pre-existing rules that open SSH
  and RDP to `0.0.0.0/0`. `your_ip` therefore does **not** restrict SSH yet.
  A dedicated VPC is planned.
