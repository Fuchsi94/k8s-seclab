# gcp-sec-lab

A 2-node kubeadm cluster (1 control plane + 1 worker) on GCE VMs (Ubuntu 24.04, Kubernetes 1.36, Cilium 1.20), used as
the base for the security AI agent lab (see [docs/roadmap.md](docs/roadmap.md)).

`terraform apply` brings up a working cluster: the startup script installs
containerd + kubeadm, the control plane runs `kubeadm init` and installs
Cilium, and the worker joins automatically.

## First time

1. Put your public **IPv4** into `terraform.tfvars`:
   ```bash
   echo "$(curl -4 -s ifconfig.me)/32"
   # allowed_ips = ["X.X.X.X/32"]  -> SSH (22) and API (6443) only from these IPs
   ```

2. Apply:
   ```bash
   terraform init
   terraform apply
   ```

3. Wait ~5 min. The bootstrap is done when this file exists on both nodes:
   ```bash
   ssh $(terraform output -raw control_plane_ip) "ls /var/lib/gcp-sec-lab-ready"
   ```
   Logs: `sudo journalctl -u google-startup-scripts -f`

4. Get the kubeconfig on your laptop:
   ```bash
   eval "$(terraform output -raw fetch_kubeconfig)"
   export KUBECONFIG=~/.kube/gcp-sec-lab
   kubectl get nodes   # both Ready once Cilium is up
   ```

## How the bootstrap works

`scripts/install-common.sh` is rendered once per role and runs as root on
**every boot**. Each step checks first whether it already happened:

| Step | Runs on | Skipped when |
|---|---|---|
| Install containerd, conntrack, kubeadm/kubelet/kubectl | both | `kubeadm` is installed |
| `kubeadm init` (public IP as cert SAN) | control plane | `/etc/kubernetes/admin.conf` exists |
| Create join token (Terraform-generated) | control plane | token exists |
| Install cilium CLI + Cilium (Hubble relay on) | control plane | `cilium` DaemonSet exists |
| Copy kubeconfig to `ssh_user` | control plane | `~/.kube/config` exists |
| Wait for API server, `kubeadm join` | worker | `/etc/kubernetes/kubelet.conf` exists |

The join token is generated by Terraform (`random_password`) and passed to
both scripts. The worker joins **without CA pinning**
(`--discovery-token-unsafe-skip-ca-verification`), which is acceptable inside
the lab network. Caveats:

- The token lives in the Terraform state and in the VM metadata. Anything
  that can reach the metadata server (including pods!) can read it while it
  is valid (24h; the control plane re-creates it on every boot). Blocking
  `169.254.169.254` for pods is a later hardening step.
- To add a node after 24h, reboot the control plane or rerun its startup
  script; that re-creates the token.

Re-run the script by hand (e.g. after `kubeadm reset`):
```bash
sudo google_metadata_script_runner startup
```

## Sandboxes

[agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox) v1.0.12
runs in the cluster. Everything lives in `k8s/agent-sandbox/` (Kustomize):

```bash
export KUBECONFIG=~/.kube/gcp-sec-lab
kubectl apply --server-side -k k8s/agent-sandbox
k8s/agent-sandbox/test.sh          # or: controller | guard | lifecycle | network | rbac
```

`test.sh` checks the setup against the live cluster and exits 1 on any
failure. The full run takes about 12 minutes (it waits for a sandbox to expire).
Right after an apply, give the API server and Cilium a few seconds to load
changed policies before running it.

| File | What |
|---|---|
| `vendor/sandbox-with-extensions-v1.0.12.yaml` | Unmodified release manifest (controller + CRDs). Upgrade = replace the file, check the SHA-256 noted in `kustomization.yaml`. |
| `manifests/00-namespace.yaml` | Namespace `sandboxes`, Pod Security `baseline` (root/`NET_RAW` allowed for scanners), warns on `restricted`. |
| `manifests/10-network-policy.yaml` | No ingress. Egress only DNS for `*.*.svc.cluster.local` / `*.*.pod.cluster.local`. Internet, metadata server, API server and other pods are blocked. |
| `manifests/20-admission.yaml` | Claims must expire (`shutdownTime` at most 24h after creation, `shutdownPolicy: Delete`) and may only set `warmPoolRef` + `lifecycle` (no pod metadata, env or volumes). Pods get no Kubernetes credentials (no token, no other service account, no projected token). |
| `manifests/30-template.yaml` | `SandboxTemplate` + `SandboxWarmPool` `default` (one pre-started sandbox). |
| `manifests/40-rbac.yaml` | ServiceAccount `sandbox-orchestrator`: may create/delete claims and exec into sandboxes, nothing else. |
| `manifests/50-quota.yaml` | At most 5 claims / 6 pods, CPU, memory and ephemeral-storage caps (sized for `w1`). |

A sandbox is requested with a claim on the warm pool:

```yaml
apiVersion: extensions.agents.x-k8s.io/v1beta1
kind: SandboxClaim
metadata:
  name: my-sandbox
  namespace: sandboxes
spec:
  warmPoolRef:
    name: default
  lifecycle:
    shutdownTime: "2026-11-23T12:00:00Z"   # required, at most 24h ahead; sandbox is deleted then
    shutdownPolicy: Delete                  # required
```

```bash
kubectl -n sandboxes wait sandboxclaim/my-sandbox --for=condition=Ready
kubectl -n sandboxes get pod -l agents.x-k8s.io/claim-uid=$(kubectl -n sandboxes get sandboxclaim my-sandbox -o jsonpath='{.metadata.uid}')
kubectl -n sandboxes exec <pod> -- sh
```

Blocked connections show up in Hubble:
`hubble observe --namespace sandboxes --verdict DROPPED` (on a node, via the
cilium agent pod).

**No Kata yet.** Sandboxes are plain `runc` containers on `w1` until the Kata
step (roadmap phase 2). Do not run untrusted or LLM-generated code in them
before that. The runtime is set in one place: the commented `patches` block in
`kustomization.yaml`.

## Notes

- The control plane public IP is **ephemeral**: it changes when the VM is
  stopped/started or recreated. The cert SAN and kubeconfig then no longer
  match; `kubeadm reset` + rerun the script, or re-issue the apiserver cert.
- Changing `k8s_version` or the script only updates the VM metadata in place.
  Running VMs keep their installed version; it applies to new VMs.
- If you work from a new place, add its IP to `allowed_ips` and `terraform apply`. Only the firewall
  rules change.
- The nodes live in their own VPC (`gcp-sec-lab-vpc`, subnet `10.30.0.0/24`).
  From outside only SSH (all nodes) and 6443 (control plane) are open, both
  only from `allowed_ips`. Between nodes everything is allowed.
- Login only with the key in `keys/lab.pub` as `ssh_user`
  (`ssh yannick@<ip>`). Project-wide keys are blocked, so `gcloud compute ssh`
  does **not** work.

## Start / stop

Set `vm_status` in `terraform.tfvars` and apply:
```bash
terraform apply -var vm_status=TERMINATED   # stop all VMs
terraform apply -var vm_status=RUNNING      # start all VMs
```
Stopped VMs only cost disk storage. Note the ephemeral control plane IP above.
